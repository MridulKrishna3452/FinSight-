# FinSight Architecture

FinSight is a monorepo with two applications (`apps/web`, `apps/api`) plus shared
infrastructure (`docker-compose.yml`) and data/ML tooling.

```
┌─────────────┐      REST (JSON)      ┌──────────────┐
│  Next.js 15 │  ───────────────────▶ │   FastAPI     │
│  apps/web   │  ◀─────────────────── │   apps/api    │
└─────────────┘   JWT access token +   └──────┬───────┘
                   httpOnly refresh           │
                   cookie                     │ SQLAlchemy 2 / Alembic
                                               ▼
                                        ┌──────────────┐
                                        │ PostgreSQL 16│
                                        └──────────────┘
                                               ▲
                                               │
                              ┌────────────────┴───────────────┐
                              │                                 │
                       ┌──────┴──────┐                  ┌───────┴──────┐
                       │   Redis     │◀──── broker ─────│ Celery worker│
                       │ (broker +   │                  │ (CSV import, │
                       │  result     │──── results ────▶│  scoring)    │
                       │  backend)   │                  └──────────────┘
                       └─────────────┘
```

## Frontend (`apps/web`)

- **Next.js 15 App Router** with route groups: `(auth)` for login/register (no
  sidebar), and top-level routes (`dashboard`, `transactions`, `budgets`,
  `insights`, `alerts`, `import`, `settings`) wrapped in `AppShell`, which
  redirects to `/login` if there is no authenticated session.
- **Auth state** (`lib/auth.tsx`) is a React context. The JWT **access token**
  lives only in memory (a module-level variable in `lib/api.ts`) — it is never
  persisted to `localStorage` or `sessionStorage`, so a page reload always
  starts by silently calling `POST /auth/refresh` (which relies on the
  httpOnly refresh cookie) to re-establish a session. See the Auth section
  below for the tradeoffs of this design.
- **Server state** is managed by TanStack Query; every list/detail view is a
  `useQuery`, every mutation invalidates the relevant query keys so the UI
  reflects the latest server state without manual refetch logic.
- **Forms** use React Hook Form + Zod resolvers (`lib/schemas.ts`) for
  client-side validation that mirrors the backend's Pydantic validation.
- **UI primitives** (`components/ui/*`) are shadcn/ui-style components: thin
  wrappers around Radix UI primitives styled with Tailwind CSS and
  `class-variance-authority`, not an installed component library — this keeps
  every component's source directly editable.
- **Charts** use Recharts (donut, bar, line, area) fed by the `insights`
  hooks.

## Backend (`apps/api`)

- **FastAPI** app (`app/main.py`) mounts a single versioned router
  (`app/api/v1/router.py`) under `/api/v1`, plus a `slowapi` rate limiter
  applied to the auth endpoints and CORS configured from `CORS_ORIGINS`.
- **Routes stay thin.** Every route handler validates input via a Pydantic
  schema, resolves the current user via the `get_current_user` dependency,
  and delegates all business logic to a service module under `app/services/`.
  This keeps ownership checks, categorization, anomaly scoring, and budget
  math testable in isolation from HTTP concerns.
- **SQLAlchemy 2.0** models (`app/models/`) use the new `Mapped[]` /
  `mapped_column()` typed style. All public-facing primary keys are UUIDv4.
  Postgres-native `ENUM` types back the Python `enum.Enum` fields; see
  `app/models/mixins.py::pg_enum` for the helper that keeps the stored enum
  *value* (e.g. `"Groceries"`) in sync with SQLAlchemy's default behavior of
  storing the member *name* (`"GROCERIES"`), which would otherwise mismatch
  the Postgres enum labels created by Alembic.
- **Alembic** migrations live under `apps/api/alembic/versions`. The initial
  migration (`0001_initial_schema.py`) is hand-written (not autogenerated)
  since it defines the full schema up front; later migrations should use
  `alembic revision --autogenerate` against a running Postgres instance.

## Auth

- **Access token**: short-lived (15 min) JWT, returned in the JSON body of
  `/auth/login`, `/auth/register`, and `/auth/refresh`. The frontend keeps it
  in memory only and attaches it as `Authorization: Bearer <token>`.
- **Refresh token**: opaque random token (not a JWT), returned as an
  `httpOnly`, `SameSite=Lax` cookie (`finsight_refresh_token`), and its
  **SHA-256 hash** is stored server-side in the `refresh_tokens` table with an
  expiry and a `revoked` flag, so a single token can be revoked (on logout) or
  rotated (on refresh) without needing a JWT blocklist.
- **Tradeoff**: keeping the access token in memory means any full page reload
  requires a round trip to `/auth/refresh` before the UI can call protected
  endpoints (see `AuthProvider`'s mount effect) — a brief loading state is
  unavoidable. This was chosen over `localStorage` to avoid XSS-exfiltrable
  long-lived tokens; the refresh cookie itself is inaccessible to JavaScript.
- Passwords are hashed with **bcrypt** via `passlib`. Auth endpoints are
  rate-limited (`RATE_LIMIT_AUTH`, default 10/minute per IP) via `slowapi`.

## Data isolation

Every service function that reads or writes a `Transaction`, `Budget`, or
`Alert` takes the authenticated `user_id` and filters by it explicitly (see
`transaction_service.get_transaction_for_user`, etc.) — there is no global
"admin" bypass. Ownership tests in `tests/test_transaction_ownership.py`
assert that a second user gets a 404 (not a 403) when touching another user's
resources, to avoid confirming that a given ID exists.

## Categorization

`app/services/categorization_service.py` implements a simple two-tier rule
engine: an ordered list of `(merchant keyword, Category)` pairs checked
against the merchant name first, then against the free-text description as a
fallback, defaulting to `Other` if nothing matches. The transaction stores
which tier produced the category (`categorization_source`: `rule`,
`fallback`, or `user_override`), and a user's manual category edit is always
recorded as `user_override` so it is never silently overwritten by
re-categorization logic.

## Anomaly / fraud-risk detection

- **Training** (`app/ml/train_anomaly_model.py`, run offline/reproducibly):
  fabricates a synthetic population of users with per-category spending
  habits, injects a small fraction (~3%) of outlier transactions (5-15x
  normal, brand-new merchant), builds the feature vector for every
  transaction via `app/ml/features.py`, and fits a scikit-learn
  `IsolationForest`. The model, its raw-score min/max (for normalization),
  and the feature name list are serialized with `joblib` to
  `app/ml/artifacts/anomaly_model.joblib`.
- **Features** (7-dimensional): log(amount), hour of day, day of week,
  category frequency, merchant frequency, and two deviation z-scores
  (amount vs. the user's own category mean, amount vs. the user's overall
  mean) — all computed identically at training time (over synthetic history)
  and inference time (over the live user's actual transaction history), so
  the model sees comparable inputs in both places.
- **Inference** (`app/services/anomaly_service.py`): on transaction create or
  CSV import, pulls the user's existing expense history, builds the feature
  vector for the candidate transaction, and asks the cached model for a raw
  isolation score, which is min-max normalized (using the training-time
  bounds) into a `0-1 anomaly_score`. `is_suspicious` is set only when the
  score is at or above `ANOMALY_THRESHOLD` (default **0.7**, configurable).
- **Explanations are rule-based, not model-derived** — Isolation Forest gives
  no per-feature attribution, so `_build_explanation` independently checks
  the same underlying deviations (amount vs. category mean, new-merchant
  status, overall z-score) to produce a human-readable sentence. Results are
  always labeled as risk indicators, never as confirmed fraud, in both the
  API response and the UI copy.

## Forecasting & insights

- **30-day forecast** (`app/services/forecasting_service.py`): aggregates
  historical daily expense totals and fits a simple linear regression
  (`numpy.polyfit`, degree 1) to project the next 30 days. The response
  includes an explicit `disclaimer` string that the UI always renders
  alongside the chart.
- **"AI" insight cards** (`app/services/insight_service.py`): fully
  deterministic — computed from month-over-month category deltas, budget
  pace-of-spend projections, subscription totals, and savings-rate trend, with
  no external LLM call. An `LLMProvider` protocol with a no-op
  `NullLLMProvider` default is defined so a real LLM could later rephrase or
  extend these cards; the app never requires an API key to function.

## Background jobs (Celery + Redis)

CSV import is the only asynchronous workflow. `POST /imports/csv` persists an
`ImportJob` row (`status=queued`) and enqueues `process_csv_import_task`
(`app/workers/tasks.py`) via Celery, using Redis as both broker and result
backend. The task loads the job, flips it to `processing`, decodes the
uploaded file, and delegates to `csv_import_service.process_import`, which:
parses/normalizes columns (with an alias map for common alternate headers),
deduplicates rows against the user's existing `dedup_hash` set, categorizes
and anomaly-scores every new expense row, and finally updates the job with a
`result_summary` (imported / duplicate / failed / suspicious counts) and
`status=completed` or `failed`. The frontend polls `GET /imports/{job_id}`
every 1.5s while the job is queued/processing.

## Currency formatting

`apps/web/lib/utils.ts` centralizes `formatCurrency`/`formatCurrencyPrecise`
around `Intl.NumberFormat`, keyed by a `currency` code (`User.currency`,
defaulting to `INR`) mapped to a locale. Adding a new supported currency is a
one-line addition to `CURRENCY_LOCALES` — no component needs to change.
